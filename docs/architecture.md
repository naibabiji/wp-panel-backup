# 最小架构与开发顺序

## 两个独立产品

源插件运行在旧站 WordPress/PHP 环境，读取本站文件与当前数据库并导出。WP Panel 运行在目标服务器，之后实现上传、校验、资源创建、导入、配置/权限和证书。插件不连接面板，两者通过版本化备份材料衔接。

## 插件职责（候选代码边界）

1. 轻量入口及一个管理员备份页面。
2. 预检/扫描：布局、地址、数据库对象、可读性、安全工作区、精确排除。
3. 导出/打包：全表 SQL、文件块、普通 ZIP、流式索引及校验。
4. 任务/维护：页面短批次推进、有界进度、三模式、明确取消。
5. 下载/清理：管理员受控下载、整套显示及已确认保留规则。

开始写代码时按实际需要建 includes/assets 等目录，不预建大量空模块。使用普通 PHP 函数/类和 WordPress 原生 API，不加前端框架/Composer 运行依赖、策略注册表或通用 Worker。持久状态/标记/锁按实际模块提出最小方案，不因原型存在临时 schema 就照搬。

## 顺序及交付

- A：当前工程/文档初始化；确定当前模块所需 Q，不影响的任务可继续。
- B：实现可安装入口、预检与基础导出，再接三模式和下载；每阶段更新任务卡，未完成能力清楚显示，不提供虚假完整备份。
- C：实际插件正常备份测试，比较路径集合/文件 SHA256 及全部表结构/数据；检查自建目录、大文件和排除选项等直接需求。
- D：插件导出样本和格式确认后，面板项目开发恢复建站；先复用既有恢复核心，不复制第二套 SQL 恢复器。
- E：最后做一次真实源插件→面板恢复的常见流程验收，发布另行授权。

不继续独立 P5/P6 原型链；HTTPS 和兼容性随对应实际模块实现验证。已有 P1–P4 作为设计证据，底层实验不逐一重做。

## 首版复杂度边界

一个管理页，备份相关的有限操作；不提前建 REST/Abilities/第三方调用 API。状态结构、路由、格式与分包参数按模块评审，有未确认产品决定不能凭实现方便定稿。代码复用以明确输入输出和格式版本即可，不提前实现面板恢复或未来方案②。

## 工作目录

- 默认在 `wp-content` 创建站点独占的随机目录，使用 WordPress 配置记录目录名及安装识别值。实际目录仍用 `site.json` 绑定源安装。目录名会留在导出数据库的选项中，复制到另一安装时旧配置不会生效。
- 目录级拒绝规则与匿名自检配合。仅对本站规范地址发起匿名请求，禁止重定向。先用公开位置的短期无敏感探测确认请求到达本站，再验证工作目录和实际任务子目录内不同类型的探测文件不可直读。首次开始、手动继续和长时间运行时复查。失败时管理员仍可取消任务或解除维护。
- 工作目录统一使用站内默认路径。扫描将当前工作目录作为精确排除项。目录随机化属于源端落盘方式，下载文件名和交换格式沿用现有约定。
