# 最小架构与开发顺序

## 两个独立产品

源插件运行在旧站 WordPress/PHP 环境，读取本站文件与当前数据库并导出。WP Panel 运行在目标服务器，接收上传的材料或通过恢复链接拉取，校验后创建站点资源、导入数据、配置权限并处理证书。两者通过 v1 备份材料衔接，源插件可独立运行。

## 插件职责

1. 管理员入口，分为创建备份和备份列表两个视图。
2. 预检/扫描：布局、地址、数据库对象、可读性、安全工作区、精确排除。
3. 导出/打包：全表 SQL、文件块、普通 ZIP、流式索引及校验。
4. 任务/维护：由管理页依次 POST 短批次、接收 JSON 进度并局部更新，同一批次操作复用现有的工作区锁和任务状态。动画随自动推进状态显示或隐藏。支持三种模式、明确取消及无 JavaScript 手动推进。
5. 下载/清理：管理员可逐份下载或下载整套 TAR，可为单套备份签发及撤销只读恢复链接。源端按保留规则轮换及清理材料。

开始写代码时按实际需要建 includes/assets 等目录，不预建大量空模块。使用普通 PHP 函数/类和 WordPress 原生 API，不加前端框架/Composer 运行依赖、策略注册表或通用 Worker。持久状态/标记/锁按实际模块提出最小方案，不因原型存在临时 schema 就照搬。

## 开发顺序及交付

- A–C 已形成 1.0.0 安装候选包。
- A：工程和文档初始化，确定各模块所需产品决策。
- B：实现可安装入口、预检与基础导出，再接三模式和下载；每阶段更新任务卡，未完成能力清楚显示，不提供虚假完整备份。
- C：实际插件正常备份测试，比较路径集合/文件 SHA256 及全部表结构/数据；检查自建目录、大文件和排除选项等直接需求。
- D：面板已实现 v1 上传和恢复链接建站，共用校验、重组及 SQL 导入流程。
- E：真实站点上传恢复及 HTTPS 链接恢复已验收。HTTP 下载与目标建站已完成隔离验收。各环境证据及发布状态见[集成文档](integrations/wp-panel.md)。

不继续独立 P5/P6 原型链；HTTPS 和兼容性随对应实际模块实现验证。已有 P1–P4 作为设计证据，底层实验不逐一重做。

## 首版复杂度边界

一个管理页承载备份操作。恢复链接使用独立的材料下载端点，授权范围限于已签发链接的单套成品。状态结构、路由、格式与分包参数按模块评审，未决的产品事项见[待定事项](pending-decisions.md)。

## 工作目录

- 默认在 `wp-content` 创建站点独占的随机目录，使用 WordPress 配置记录目录名及安装识别值。实际目录仍用 `site.json` 绑定源安装。目录名会留在导出数据库的选项中，复制到另一安装时旧配置不会生效。
- 首次开始备份会准备目录并创建 Apache 的 `.htaccess`、IIS 的 `web.config` 与本地安装标记。工作目录和任务子目录均生成 `index.php` 和 `index.html`。服务器负责执行静态文件禁访规则。已完成备份的下载列表提示直接 URL 的风险并显示 Nginx 配置示例，启动及继续均无需 HTTP 回环。
- 工作目录统一使用站内默认路径。扫描将当前工作目录作为精确排除项。目录随机化属于源端落盘方式，下载文件名和交换格式沿用现有约定。

## 分包与下载

- 文件块和 HTTP 批次与 ZIP 载荷预算独立。任务启动时保存分包档位，单个文件处理请求最多复制 64 MiB，到达预算或完成扫描后在独立请求中压缩该包。任务状态保存后可跨请求继续；生成并记录 ZIP 后清理暂存块。
- 下载列表支持直接逐份下载或将同套文件流式封装为一个 TAR。两种方式共用管理员授权和保留期限，TAR 不占用整套副本空间。
- 下载共用固定 1 MiB 上限的二进制读取和输出，发送响应头之前清理 PHP 输出缓冲，避免后台插件把各块重新积累在内存中。后台下载校验管理员权限及 nonce，恢复链接端点校验单套备份的凭据、有效期及请求材料。响应长度按已打开的材料计算，TAR 头、对齐填充及结束块沿用现有布局。

## 数据库导出推进

- 数据库阶段的同一个 HTTP 请求最多连续执行同一张表的 8 个导出步骤，每步保存原有检查点。经过约 2 秒后停止开始后续步骤，每个已开始的步骤按原规则完成。浏览器在数据库或文件分包阶段等待 75 毫秒后发下一次请求。同一页面仍只有一个进行中的请求，启动和扫描阶段沿用 300 毫秒间隔。
